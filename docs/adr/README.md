# 架构决策记录（ADR）

本目录用「架构决策记录（Architecture Decision Record）」沉淀本项目的重要技术决策，并配合「多 Agent 开发模式」把每个决策拆解、分头实现、再汇总验收。

## 什么是 ADR

ADR 是一份轻量、不可变、带编号的文档，记录**一个**架构/技术决策的：

- **背景（Context）**：为什么现在要做这个决策，有哪些约束与压力。
- **决策（Decision）**：最终选择了什么方案。
- **后果（Consequences）**：好处、代价、风险、后续要注意的事。

一条 ADR 一旦被接受就不再修改内容；要改变方向时，新建一条 ADR 并把旧的标记为 `已废弃（Superseded by ADR-XXXX）`。这样决策的演进历史是可追溯的。

## 状态流转

```
草案(Proposed) → 已接受(Accepted) → 已废弃(Superseded) / 已弃用(Deprecated)
```

## 命名与编号

- 文件名：`NNNN-短横线标题.md`，`NNNN` 为四位递增编号（`0001`、`0002` …）。
- 模板：复制 [`0000-template.md`](<0000-template.md>) 另存为新编号。
- `0000-template.md` 只是模板，不计入正式决策。

## 工作流：ADR 驱动的多 Agent 开发

每一项需要架构/技术判断的工作，按以下闭环推进：

1. **立项**：识别出一个需要决策的问题（新功能、重构、依赖/协议选型、性能或可靠性改造等）。
2. **写 ADR（草案）**：用模板起草 ADR，列清背景、候选方案、取舍，给出推荐决策。此时状态为「草案」，需与用户确认后置为「已接受」。
3. **拆解为可并行的子任务**：在 ADR 的「实施计划」小节里，把决策拆成**相互独立、边界清晰**的工作包（例如：某监控类型模块、API 层、数据库迁移、告警规则、测试）。
4. **多 Agent 并行实现**：每个独立工作包派发给一个子 Agent 并行推进；有依赖关系的工作包串行安排。
5. **汇总与验证**：合并各子 Agent 的产出，统一跑 `cargo build` / `cargo test`，解决交叉冲突。
6. **回填 ADR**：把实现中偏离原决策的地方、新发现的后果补回 ADR 的「后果」小节；必要时另起 ADR。

### 什么时候值得写 ADR

- 影响多个模块或对外接口的改动。
- 引入/替换依赖、协议、存储或并发模型。
- 有多个合理方案、需要权衡取舍的选择。
- 对性能、可靠性、安全性有长期影响的决定。

一次性的小 bug 修复、措辞调整、显而易见的实现细节**不需要** ADR。
