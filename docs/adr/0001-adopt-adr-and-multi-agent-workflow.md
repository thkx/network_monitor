# ADR-0001：采用 ADR + 多 Agent 开发工作流

- 状态：已接受
- 日期：2026-09-25
- 决策者：项目维护者
- 相关：本目录 [`README.md`](<README.md>)

## 背景（Context）

`network_monitor` 已发展为含 12 种监控类型、告警状态机、Diesel/SQLite 持久化与 actix-web API 的中型 Rust 项目，模块边界相对清晰（`monitor/`、`alerts/`、`api/`、`database/`、`domain/`、`tools/`）。随着功能扩张，出现两类问题：

- 技术决策（协议语义、TLS 栈统一、分页策略、告警抑制等）散落在代码注释与 commit 里，缺乏集中、可追溯的记录，新改动容易与既有决策冲突。
- 多个相互独立的模块（不同监控类型、API 层、迁移、告警规则、测试）常常可以并行推进，但以往是串行开发，吞吐受限。

需要一个既能沉淀决策、又能提升并行开发吞吐的协作方式。

## 候选方案（Options）

1. **仅口头/commit 记录决策，串行开发** — 优点：零流程成本；缺点：决策不可追溯、并行度低。
2. **引入 ADR，但仍串行开发** — 优点：决策可追溯；缺点：没有解决吞吐问题。
3. **ADR + 多 Agent 并行开发（本决策）** — 优点：决策可追溯 + 独立工作包并行落地；缺点：需要前期把任务拆成边界清晰的工作包，并在合并时做集成验证。

## 决策（Decision）

采用方案 3：

- 每个需要架构/技术判断的工作，先写一条 ADR（草案 → 用户确认后置为「已接受」）。
- 在 ADR 的「实施计划」小节把决策拆成相互独立、边界清晰的子任务，标注依赖关系。
- 独立子任务派发给多个子 Agent 并行实现，有依赖的串行安排。
- 合并后统一 `cargo build` / `cargo test` 做集成验证，并把实现偏差回填 ADR。

详细流程见 [`README.md`](<README.md>) 的「工作流」小节。

## 实施计划（可并行的子任务）

- [x] 子任务 1 — `[独立]` 建立 `docs/adr/` 目录与 `README.md` 索引说明。
- [x] 子任务 2 — `[独立]` 提供 `0000-template.md` ADR 模板。
- [x] 子任务 3 — `[依赖 子任务 1/2]` 以本 ADR 记录工作流本身的采用决策。

## 后果（Consequences）

### 正面

- 关键技术决策集中、带编号、可追溯，新改动有据可依。
- 独立模块可并行开发，提升吞吐。
- ADR 的「实施计划」天然成为多 Agent 的派发清单。

### 负面 / 代价

- 每个重要决策多出一份文档的书写成本。
- 任务拆分不当会导致子 Agent 产出在合并时冲突，需要集成阶段兜底。

### 风险与跟进

- 若后续更换决策记录工具或流程（如改用 MADR 严格格式、接入 adr-tools），另起新 ADR 并将本条标记为「已废弃」。
- 多 Agent 并行的边界划分质量直接影响集成成本，需在每条 ADR 的实施计划里显式标注依赖关系。
